Analytic continual learning, from scratch

My working notes on RanPAC and the little family of methods around it: freeze the network, learn the last layer in one closed-form equation, and keep no old data. I kept my own margin notes in, next to the figures they belong to.

These are my own notes on RanPAC [2] and the analytic methods around it. I keep coming back to this corner of continual learning because it's one of the few places where the whole method fits in your head: freeze a pretrained network, and learn the final linear layer in closed form. No replay buffer, no gradient steps on the stream. I wrote this the way I'd explain it to someone sitting next to me, so I've kept the equations but tried to say what each one is actually doing. By the end you'll see the exact question my own paper picks up.

Forgetting, and why it happens

Class-incremental learning is the annoying version of the usual setup. The model sees classes in chunks — one task at a time — and once a chunk has gone by, its data is thrown away. Then you test on everything seen so far, with no hint about which task a test image came from.

Train a network the normal way on a stream like this and it does the obvious bad thing. Learning the new classes rewrites the weights that were carrying the old ones, and accuracy on the early tasks can fall almost to zero. The dramatic name is catastrophic forgetting, and it's fair: the damage really is that abrupt.

The two textbook defenses both pay for it somewhere. Replay keeps a buffer of old examples and mixes them back in — but storing data is exactly what a lot of real settings won't allow, whether for privacy or just for space. Regularization adds a penalty that discourages important weights from moving, which protects the old classes but slows down learning the new ones. Notice that both still do the thing that caused the problem: they keep updating the whole network by gradient descent, and then try to manage the fallout.

Don't train the network

The analytic methods make a blunter choice. Don't train the network at all. Take a pretrained backbone f, freeze it, and only ever touch a linear layer sitting on top of its features. If you never send a gradient back through the features, they can't drift — so in the usual sense, there is nothing left to forget.

That feels like it throws away too much, until you remember what a frozen backbone hands you for free. A linear layer trained with squared-error loss is just ridge regression, and ridge regression has a closed-form solution. One equation, no iterating. If X stacks the features of your data row by row and Y their one-hot labels, the best weights are:

W = (XTX + λI)−1 XTY   // ridge readout; λI keeps it invertible

The part I want to flag is what this depends on. It never asks for the individual images back — only two summaries of them: XTX, how the feature coordinates correlate with each other (this is the Gram matrix), and XTY, how features line up with labels. Both are just running sums. A new task arrives, you add its share to each sum, and re-solve. That's the whole trick, and everything below is detail on how to make it actually work well.

my margin note

ridge · (XᵀX + λI)⁻¹  →  λI because XᵀX (= G later) can be singular when some feature dims are linearly dependent. no λ → can't invert.

Class prototypes, and where they break

Before the clever version, the simplest thing you can build on frozen features is a class prototype. For each class, average the feature vectors of its training images. That average cy is the prototype — a single point standing in for the class. To classify a test feature f, compare it to every prototype by cosine similarity and take the closest:

sy = fTcy / (∥f∥ · ∥cy∥)   // cosine to each class mean (NCM / Eqn 1)

This is the nearest-class-mean (NCM) classifier, and for continual learning it's genuinely appealing — the prototypes don't care what order the tasks came in, and you store one small vector per class instead of a buffer of images. The problem is that it's not very accurate, and the reason is subtle enough that it took me a while to see it.

Pretrained features are informative, but the class prototypes you get from them point in similar directions. The prototype for "dog" and the prototype for "cat" share a lot of the same high-firing coordinates, because the backbone describes everything with the same generic vocabulary. So the prototypes are strongly correlated across classes, and cosine similarity — which only sees angles — can't cleanly separate directions that are already bunched together. You get poorly calibrated similarities and a lot of confident mistakes.

my margin note

simple, raw CPs → high corr between classes → cosine sim poorly calibrated → poor separation.

eqn (2) / decorrelate → better separation.

The fix: second-order statistics

The repair is small to write and does a lot. Instead of plain cosine, score a test feature against each class with the Gram matrix sitting in the middle:

sy = fT G−1 cy   // Gram-matrix readout (Eqn 2); G = feature correlations

G records how every feature coordinate relates to every other across all the data — a second-order statistic, where a prototype is only a first-order average. Multiplying by G−1 is a whitening step: it cancels the correlation structure the prototypes were all sharing, so that what's left is what makes each class different. It's close in spirit to LDA, and it drops straight out of the least-squares objective we started from — the ridge solution and this score are the same machinery viewed two ways.

my margin note

2nd-order stats (G) > first-order (just cᵧ).

raw cᵧ assume Gaussian w/ isotropic cov → empirically false. G⁻¹ = decorrelate → fixes the geometry.

In practice you regularize it, (G + λI)−1, because G can be singular when some feature directions are redundant — which, with pretrained features, they often are. The λ is picked by cross-validation and keeps the inverse well-behaved. (This is the ridge·c I'd scrawled next to the equation.)

Why this is already continual

Here's the part that makes all of this safe for a stream, and it's worth slowing down on. The two things you keep are G and C (the stacked class prototypes), and both are nothing but sums over samples:

G = Σt Σn ht,n ⊗ ht,n     C = Σt Σn ht,n ⊗ yt,n   // Eqn 4: outer-product sums

A new task is just more terms in the sums. And addition doesn't care about order — so learning the tasks one at a time, adding each task's contribution as it comes, lands on the exact same matrices you'd get from training on all the data at once. ACIL [1], the method that set up a lot of this, calls that property absolute memorization: the incremental answer is algebraically identical to the joint answer, so there's no approximation and nothing to forget.

my margin note

G, C = ΣΣ outer products → invariant to task order → this is what makes it continual learning.

keep only G, C — never the images → private by construction.

And since you only ever hold G and C, never the images, the method is private without trying. There's also a recursive identity that updates the inverse of G when a task arrives, so you never re-invert the whole thing from scratch — nice to have, but the sum intuition above is the thing I actually keep in my head.

This is the bit I find genuinely satisfying: forgetting isn't being fought with a penalty here, it's ruled out by the algebra. The incremental update just is the joint solution.

Random projections: going wider

Everything so far gets you a decent continual classifier. RanPAC's actual contribution is what it slips in before the readout. Take the frozen features of length L, multiply by a random matrix W to blow them up to a much larger size M > L, and push the result through a nonlinearity (a ReLU). W is drawn once, at random, and never trained. Then run the same Gram-matrix readout on these wider features.

sy = φ(fTW) (G + λI)−1 cy   // Eqn 5: random projection W, nonlinearity φ, then the readout
my margin note

W for high M → creates feature interactions. DON'T learn it — random & frozen.

φ (ReLU/square) is the point; w/o nonlinearity, RP barely beats no-RP.

My first reaction was: how can a random map help, when it adds no new information? The paper gives two reasons, and they're the two observations I circled in the margin.

One: as M grows, the projected features start to look like an isotropic Gaussian — a nice round blob with no preferred direction. That matters because the Gram-matrix readout quietly assumes roughly that shape (that's the Gaussian-with-isotropic-covariance assumption the raw prototypes violated). So widening doesn't add information, it reshapes the features into the distribution the classifier was built for, and the fit gets better.

Two: in a high enough dimension, two different inputs almost always land at distinct angles. Directions that were tangled together in the original L-dimensional space get room to spread out, and a straight-line boundary that couldn't separate them before suddenly can. More width, more linear separability.

my margin note

2 observations ⇒ why RP works:

(1) large M → dist ≈ isotropic Gaussian → good for the Gram/Eqn-2 fit.

(2) large M → angles between instances more distinct → more separable.

The nonlinearity is doing real work here, not decoration. Without the ReLU, the wide random projection is still a linear map of the features, so it can't create anything the linear readout couldn't already reach — and the paper's Figure 3 shows accuracy basically flat in that case. With the nonlinearity, the projection mixes coordinates into genuine interaction terms, and accuracy climbs steadily as M grows. That's the whole reason to go through the trouble.

One exception: the first task

There's a loose end. A backbone pretrained on ImageNet might just not describe your new domain well — medical scans, satellite images, whatever. Frozen features that are wrong for the data can't be rescued by any readout on top.

RanPAC's answer is to allow a little adaptation, but only on the very first task, using a parameter-efficient method (PETL — adapters, SSF, VPT, the usual lightweight options). Tune on task one, then freeze that too and never touch it again. The first task is the one safe place to adapt, because it's the single moment when you have a real chunk of data and no past tasks to damage. After that, you're back to the frozen-plus-closed-form world for the rest of the stream.

my margin note

pretrained fea not suitable w/ new data → learn PETL.

but ONLY first session (have data, no past to forget) → freeze after.

What you actually carry

Now the tension that actually pulls me into this. The expansion wants to be wide — that's where the accuracy comes from. But the thing you have to carry between tasks is G, the Gram matrix of those widened features, and G is M × M. Double the width and you quadruple the state. At M ≈ 10,000 that's a matrix with a hundred million entries — hundreds of megabytes whose only job is to record how the coordinates interact.

So "wider is better" runs straight into a budget. If the state you carry has to stay small — picture many separate task streams sharing one frozen backbone, each keeping its own readout — you simply can't make the expansion as wide as you'd like. Something has to give: fewer coordinates, or a cheaper way to store how they interact.

Where this goes

That collision is the question my current work takes up. Given a fixed memory budget, is it better to spend it on more width, or on storing the interactions among a smaller set of coordinates more faithfully? The method and the answer are in a paper under review, so I'm not posting them here yet — but the next note sets up the question properly.

If the setup in these notes now feels obvious, that's the point.
